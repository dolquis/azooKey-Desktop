# 状態語を定義文へ書き換える

検出される語彙は `python3 scripts/docs-lint.py --print-words` で得る。ここには列挙しない。書き写した語彙リストは、スクリプト側が変わった日に無言で嘘になる。

語彙は 2 段に分かれる。

- **strong** は単独で検出する。それだけで現在の状態を主張し、いつ嘘になったか読み手に分からないためである。
- **weak** は Issue / PR 参照と同じ行にあるときだけ検出する。「現行の開発対象は Windows 版」のような正当な用法が多い一方、追跡番号の隣に置かれた状態語は、その文書がトラッカーを写している証拠になるからである。

日付を含む行は検出しない。日付があれば過去の事実の記録として読まれ、腐らない。ただしこの免除は**見出しには適用しない**。見出しには日付を添える余地がなく、拾い読みの対象になるためである。

## 書き換えの型

| 状態語を含む例 | 定義文への書き換え |
|---|---|
| 「現状 X は gguf を probe するのみ」 | 「X は GGUF 指定時のみ実推論を行う。未指定時は Y へフォールバックする」（振る舞いの定義） |
| 「Y は未実装（M11 / M30）」 | 実装済みなら記述ごと削除。未実装が事実なら「M11 / M30 が Y を実装する」（責務の定義） |
| 「暫定的に `--typo-mode` を使う」 | 採用するなら状態語なしで仕様として確定する。採用しないなら記述ごと削除する |
| 「M46 完了後に配線する」 | 「M46 の PrivacyGate が利用可能なときのみ判定する」（機能条件。時系列ではない） |
| 「DEV-223 は中止された」 | Linear へ。repo docs には経緯を残さず、確定した仕様だけを書く |
| 「157 件中 156 passed」 | 削除。テスト結果は実行のたびに変わり、文書は追随できない |
| 「`Foo.cpp:123` を参照」 | 関数名・クラス名までに留める。行番号はリファクタで即座に陳腐化する |
| 「## 0. 現状サマリ（2026-06-09 時点）」 | 見出しごと削除するか、内容を定義文へ移して見出しを主題名にする |
| 「### P1-1. オンボーディング ✅ 完了 (PR #7)」 | 「### P1-1. オンボーディング」。完了は Linear の Done が正典 |
| 「### P3-6. 環境ハードニング（未着手）」 | 「### P3-6. 環境ハードニング」。未着手は Linear の状態から導出できる |

## 判断の軸

書き換えるか削除するかは、その記述が**定義**か**実況**かで決まる。

- 定義は「X は Y する」「A の完了は B の前提である」のように、いつ読んでも同じ意味を持つ。残す。
- 実況は「今どうなっているか」を語る。Linear から導出できるなら削除し、導出できない事実（設計上の制約、既知の限界）なら定義文へ言い換える。

依存関係としての「M46 完了」は、マイルストーンの依存グラフを表す限りにおいて定義である。疑わしいときは機能条件の文へ書き換えるほうが安全になる。

## 免除を使う前に

`<!-- lint:allow status -->` は個別の誤検知に使う。多用すると検査の意味が薄れる。同じ文書で何度も使いたくなったら、その文書は生きた定義ではなくスナップショットである可能性が高い。文書単位の `lint:allow-file` か `docs/archive/` への移動を先に検討する。

何も抑止しなくなった免除コメントは `dead-allow` として検出される。行を直したら免除も一緒に消す。
