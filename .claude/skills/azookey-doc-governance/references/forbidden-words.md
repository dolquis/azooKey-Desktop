# 状態語の書き換え（azooKey の例）

語彙の正典は `scripts/docs-lint.py` である。ここへ書き写すと、それ自体が無効化されないキャッシュになり、語彙が更新された日に無言でずれる。次で得る。

```
python3 scripts/docs-lint.py --print-words
```

出力は 2 段に分かれる。strong は単独で検出され、weak は Issue / PR 参照と同じ行にあるときだけ検出される。weak が単独で出ないのは、「現行の開発対象は Windows 版」のような正当な用法があるためで、トラッカーの写しになっている行だけを拾う設計である。

`status` は HEURISTIC で、過検出を前提にファイル単位の件数だけが出る。件数をゼロにするのは目的ではない。件数の多いファイルは、たいてい生きた定義ではなく凍結すべき記録である。

検査の対象外は `docs/linear-conventions.md`（状態運用そのものが主題）と `docs/archive/`（完了した記録）。除外の既定値は `scripts/docs-lint.py` にあり、この repo の差分は `.docs-lint.toml` にある。

## 書き換えパターン

| 状態語を含む例 | 定義文への書き換え |
|---|---|
| 「現状 `ZenzaiModelConverter` は gguf を probe するのみ」 | 「`ZenzaiModelConverter` は GGUF 指定時のみ実推論を行う。未指定時は SimpleConverter へフォールバックする」 |
| 「`azookey_settings.exe` は未実装（M11/M30）」 | 実装してあるなら削除。まだなら「M11/M30 が `azookey_settings.exe` を実装する」 |
| 「暫定的に `--typo-mode` を使う」 | 採用するなら状態語なしで仕様として確定。採用しないなら記述ごと削除 |
| 「M46 完了後に配線する」 | 「M46 の PrivacyGate が利用可能なときのみ判定する」（機能条件。時系列ではない） |
| 「DEV-223 は中止された」 | Linear へ。repo docs には経緯を残さず、確定した仕様だけを書く |
| 「157件中156 passed」のような実測件数 | 削除。CTest の結果は実行するたびに変わり、docs は追随できない |
| 行番号付きコード参照（`Foo.cpp:123`） | 関数名・クラス名までに留める。行番号はリファクタで即座に陳腐化する |

## 許容される例外

- 依存関係としての「M46 完了」（roadmap の「前提」欄など、milestone の依存グラフを表す場合）は検査の対象外になりうるが、疑わしいときは機能条件の文へ書き換える方が安全。
- チェックリスト文書（`docs/handoff/*.md` の一部）で「☐ 既知(DEV-xxx)」のように中立的な追跡リンクとして DEV 番号を使うのは許容する。「DEV-xxx が Done」のような状態記述にしない。
- 意図的な誤検知は `<!-- lint:allow status -->` をその行または直前行に置いて免除する。多用しない — 免除が増えるほど検査の意味が薄れる。何も抑止しなくなった免除は `dead-allow` として報告される。
- 更新しない前提の調査レポート・スナップショットは、先頭に `<!-- lint:allow-file line-ref,status -->` を置くか `docs/archive/` へ移す。ファイル単位の免除は「これは記録である」という宣言を兼ねる。
