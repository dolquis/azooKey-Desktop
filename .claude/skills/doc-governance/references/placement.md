# 情報と文書の置き場所

同じ内容を 2 箇所に書かない。ここで決めた場所が正典で、他の場所はリンクだけにする。

## 情報の置き場所を決める

| 情報種別 | 正典 | 他の場所での扱い |
|---|---|---|
| 状態・進捗・優先度・担当・サイクル | Linear | repo docs には書かない |
| 課題トラッキング | Linear | GitHub Issues は mirror |
| 機能仕様（データ構造・schema・永続化形式・責務境界・fallback・設定項目・ユーザー可視挙動） | 対応する spec 文書 | 引用するときは「正典は X」の 1 行 + リンク |
| マイルストーン定義・依存関係・受け入れ条件の「定義」・スコープ・リスク | roadmap 1 本 | 受け入れ条件を spec 側へ二重に書かない。roadmap は達成状態を持たない |
| ビルド・テスト手順 | README | 他の文書は差分（CI 固有の引数など）だけを書く |
| Linear 運用のルール本文 | linear-conventions の共有コア節（origin のベンダリングコピー） | AGENTS.md は要約。詳細は追わずリンクする |
| Linear 運用の repo 固有差分 | linear-conventions の Project Delta 節 | この repo で編集してよい唯一の Linear 運用節 |
| ドキュメント一覧・索引 | `docs/README.md`（無ければ README の案内） | 新規文書を追加したら必ず載せる |

この表は雛形である。repo ごとの実体（spec のファイル名、roadmap のパス）を埋めて **その repo の AGENTS.md に置く**。スキル側には置かない。置き場所が既にある情報を 2 箇所目へ写すことになり、防ごうとしている陳腐化そのものを作るからである。

## 正典マトリクスが無い repo での作り方

AGENTS.md に「正典（Source of Truth）の分担」節を作り、上の表から実在する行だけを写す。AGENTS.md 全体の骨子は `dolquis/agent-ops` の `templates/AGENTS.md` から起こし、常時ロードには安全規則、正典表、作業種別ごとの参照表、検証と PR の最小規約だけを残す。存在しない文書の行は書かない。書いた直後に `python3 scripts/docs-lint.py --category link --category section` を実行し、参照先が実在することを確かめる。

## 正典宣言は双方向にする

A が「正典は B」と書いたら、B 側にも「本節は A から参照される」の 1 行を置く。片方向の宣言は、B の内容が変わったときに A が追随しない事故を生む。参照される側が自分の被参照を知っていれば、変更のたびに追随先が見える。

## 文書の種別と置き場所

| 種別 | 特徴 | 置き場所 | 索引 |
|---|---|---|---|
| 機能仕様 | ユーザー可視挙動・データ構造・責務境界の定義。恒常的に更新される | `docs/*-spec.md` など | 索引に必須 |
| 開発計画 | マイルストーン定義・依存関係・受け入れ条件の定義 | roadmap 1 本（新規ファイルを作らない） | roadmap 自体が唯一なら索引不要 |
| 恒常 runbook | 実機検証・診断・環境構築など繰り返し使う手順 | `docs/handoff/` など固定の場所 | 索引に必須 |
| 一回限りの引き継ぎ | 特定のセットアップ・移行の一度きりの指示書。DoD を持つ | 作業中は runbook と同じ場所、DoD 達成後は `docs/archive/` | archive 後は索引から外す |
| 参考資料・調査記録 | 特定時点のスナップショット。更新しない前提で書かれる | `docs/` | 索引に載せ「正典ではない」と明記する |
| 決定ログ・監査記録 | 日付つきの過去の事実 | `docs/decisions/` など | 索引に載せる。状態語を含んでよい |
| 運用規約 | repo 横断の作業ルール | `docs/linear-conventions.md`、AGENTS.md（要約） | 索引に必須 |

## 一回限り文書を archive するタイミング

1. 文書自身が DoD チェックリストを持つ場合、そのチェックリストを実体（ファイルの存在、設定の実在）と照合する。
2. 全項目が達成済みなら `git mv` で `docs/archive/` へ移す。
3. 移動先の冒頭に、アーカイブである旨と、再利用する場合の注意を 1〜2 行で足す。相対パス参照は、再利用時にそのまま使える雛形として機能するなら書き換えない。
4. その文書を指す索引・説明文を更新する。移動でリンクが切れていないか `--category link` で確かめる。

## スナップショット文書の扱い

更新しない前提の調査記録・提案書・監査記録は、状態語と行番号参照を大量に含む。これらは archive するか、文書の先頭に `<!-- lint:allow-file heading-state,status,line-ref -->` を置く。この 1 行は検査の免除であると同時に、「この文書は特定時点のスナップショットである」という読み手への正直な宣言になる。

## 1 ファイルに複数の単位が同居する場合

1 つの spec が複数のマイルストーンを扱うのは、機能的に地続きなら問題ない。冒頭に「節 → 単位」の対応表を置き、どの節がどの範囲かを読み手が迷わないようにする。§ 番号を外部から参照されている場合、番号を維持したまま拡張する。分割と改番は、外部参照をすべて洗い出してから検討する。

## README を簡潔に保つ

README は簡潔な紹介文書として保つ。詳細手順が伸びてきたら、コマンド例だけ残して詳細を該当文書へリンクする。「## 状態」「## 進捗」「## TODO」のような、時系列で陳腐化する見出しを追加しない。
