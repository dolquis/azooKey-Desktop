# 日本語技術文書の文章規範

日本語の README、仕様書、ADR、runbook、技術記事、書籍原稿を作成または推敲するときに使う。
短い箇条書き、コミットメッセージ、翻訳、コードだけの変更には使わない。

## 共通原則

- 確認していない事実を補わない。推量、可能性、反実仮想は、根拠なしに断定へ変えない。
- 用語、分類、責務の境界を文書全体で揃える。異なる原因や判断を一つの語でまとめない。
- 一つの段落では一つの論点を進め、段落の冒頭で役割が分かるようにする。
- 同じ主張を言い換えて繰り返さず、装飾的な前置きより主張と根拠を直接書く。
- コード、設定、ログ、識別子は正確に保ち、変更する場合は実体を確認する。

## 必要な reference の選択

作業に必要な reference だけを読む。無条件に全て読まない。

- Markdownの表記、定義、見出し、コードブロックを整える場合は [formatting.md](references/formatting.md) を読む。
- 段落の順序、因果、反論、説明の飛躍を直す場合は [argument-structure.md](references/argument-structure.md) を読む。
- 冗長さ、語り口、過剰な演出、LLMらしい空句を直す場合は [style-and-concision.md](references/style-and-concision.md) を読む。
- 書籍章や全面リライトのように三領域すべてが対象になる場合だけ、三つを全て読む。

論証の再配置が主目的なら `argument-gap-edit` を併用する。

## 作業手順

1. 文書の目的、読者、公開先、変更範囲を確定する。
2. 既存文書では、事実、用語、識別子、引用、意図的な不確実性を保護対象として確認する。
3. 作業内容に対応する reference を選び、構成、文体、表記の順に直す。
4. 主張と根拠、段落間の受け渡し、用語の一貫性、重複を再確認する。
5. lintを利用できる場合も機械的に従わず、文脈と既存規約に照らして採否を決める。
6. 報告は変更の規模に合わせ、重要な変更と未確認事項だけを簡潔に示す。
