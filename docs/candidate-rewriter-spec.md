# 候補リライター仕様

本書は候補リライター層（`plans/windows-port-roadmap.md` M62）の機能仕様の正典である。
IPC payload、データ形式、TIP と Host の責務境界、候補窓 UX、確定時の学習 reading の扱い、
ライセンス境界を定める。進捗と状態は持たない（状態の正典は Linear。`AGENTS.md`「Linear
運用（管制塔）」参照）。

関連 spec:

- `docs/legacy-parity-spec.md` … 入力パイプライン（§1: UserAction / InputState /
  ClientAction）と候補窓（§3）。§10 の候補窓 UX はこのパイプライン上に載る。
- `docs/native-ui-spec.md` … 候補ウィンドウの描画層。カラー絵文字の描画は §3.4 が正典で、
  本書 §10.1 はその上に置く view-model だけを定める。
- `docs/licensing-policy.md` … 第三者資産 attribution の運用規約。§15 はこれを参照し、
  三層 attribution モデル自体を再定義しない。
- `docs/windows-tsf-host-architecture.md` … IPC メッセージと互換性優先の実装ルール。
  §8 の payload 追加はこの規約に従う。

## 1. 目的

候補リライターは、既存の変換候補または入力中の読みから派生候補を生成する層である。

M62-A では、ASCII の十進数字だけで構成される読みを対象に、数字の異表記候補を生成する。

M62-B では、純かなの読みからカタカナの異表記候補を生成する（§18）。英字の異表記は M60 が
受け持つ（§18.8）。

M62-C では、かな読みから記号候補を生成し、記号の関連候補を候補列へ広げる（§19）。

M62-D では、かな読みと Slack 風の `:trigger` 検索から絵文字候補を生成する（§6 以降）。

## 2. 共通方針

リライターは既定で無効にする。

無効時は候補列、確定文字列、学習データを変えない。

候補の表層形と注釈は分離する。

確定文字列には注釈を含めない。

TIP ローカルに注入する候補は、IPC payload の候補表現へは流さない。

Host 側でデータ駆動のリライターを扱う段階では、IPC の候補 payload に注釈欄を追加する
（§8.2）。

## 3. M62-A 数字リライター

M62-A の対象は、空でない ASCII 十進数字列である。

`20世紀`、全角数字、空文字列、`uint64_t` を超える値は対象外とし、候補を返さない。

生成する候補は、漢数字、大字、丸数字、ローマ数字、16 進数、8 進数、2 進数である。

丸数字は 0 から 50 までを対象にする。

ローマ数字は 1 から 12 までを対象にし、大文字と小文字の Unicode ローマ数字を生成する。

範囲外の丸数字とローマ数字はスキップする。

16 進数、8 進数、2 進数は `uint64_t` に収まる値だけを対象にする。

表層形が入力文字列と同じ候補は追加しない。

`settings/mvp-settings.schema.json` の `numberRewriter`（boolean、既定 `false`）が
M62-A 全体の有効化を制御する。
Host は runtime settings の値を Handshake 応答へ載せ、TIP は通常の変換候補を受信した後に
数字候補をローカルで追加する。
Handshake 応答に設定値がない旧 Host は `false` として扱う。

`numberRewriter == true` かつ一括変換ではないとき、TIP は ASCII 数字を生成する主キーと
テンキーを composition へ取り込み、通常の候補要求へ読みとして渡す。
Shift などによって数字以外を生成する主キーは取り込まない。
候補窓が開いているときの `1` から `9` は、従来どおり候補の直接選択を優先する。
`numberRewriter == false` のとき、数字キーは従来どおりアプリへ渡す。

TIP は Host 候補を先に保ち、その末尾へ数字候補を追加する。
同じ表層形がすでに Host 候補または先行する数字候補にある場合は追加しない。
一括変換、ライブ変換、予測候補の経路には数字候補を追加しない。

同じ表層形が複数の分類から生成された場合は、先に生成した候補を残す。

## 4. 注釈

各候補は `Candidate::description` に和文注釈を持つ。

M62-A で使う注釈は次のとおりである。

- `漢数字`
- `大字`
- `丸数字`
- `ローマ数字（大文字）`
- `ローマ数字（小文字）`
- `16進数`
- `8進数`
- `2進数`

M62-C の記号候補は、注釈に記号の和名を用いる（§19.6）。

M62-D の絵文字候補は、注釈に絵文字の和名を用いる（§7.2 の `name_ja`）。

## 5. ライセンス境界

M62-A はコード内の固定テーブルと一般的な数値変換アルゴリズムだけで実装する。

Mozc 由来データには依存しない。

M62-C と M62-D で Mozc 由来データや CLDR データを使う場合は、データファイルの著作権表示と
集約ライセンス文書を追加する。記号データの具体的な要件は §19.11、絵文字データの具体的な要件は
§15 が定める。

## 6. M62-D 絵文字リライターの範囲

M62-D は、次の 2 つの入力経路から絵文字候補を生成する。

- **かな読み引き**：変換対象の読みが絵文字の読みと一致するとき、絵文字候補を候補列の末尾へ
  追加する（`わらい` → 😄）。
- **`:trigger` 曖昧検索**：ASCII の `:` に続けて打鍵した英数字列を検索語として扱い、絵文字
  だけの候補列を出す（`:smile` → 😄）。

どちらも `emojiRewriter == true` のときだけ動作する（§13）。

本節以降は次を非目標とする。

- **絵文字の学習と並べ替え**。確定した絵文字は学習ストアへ書かない（§12）。順位はデータ由来の
  `rank` と決定的な順序規則（§9.4）だけで決まる。
- **タイポ許容**。`:trigger` 検索は編集距離による補正を行わない（§9.3）。
- **肌色修飾子の展開**。修飾子付きシーケンスをビルド時に自動生成しない（§7.3）。
- **ライブ変換と予測候補への注入**。絵文字候補はどちらの経路にも載せない（§10.3）。
- **英数モードでの `:trigger`**。`:` の取り込みは `inputMode == "hiragana"` に限る（§11.1）。

## 7. 絵文字データの形式と再ポート

### 7.1 配置と供給

絵文字データは `inference-host` が読む単一の TSV ファイルであり、Host バイナリと同じ配布
単位に含める読み取り専用資産として扱う。既定パスは Host の実行ファイルと同階層の
`data/emoji.tsv` とし、`emojiDataPath` で上書きできる（§13）。

`bracket-pairs.tsv`（`docs/bracket-pairing-spec.md` §4.5）と異なり、本ファイルはユーザー編集を
前提としない。ホットリロードも提供しない。ユーザーが `%LOCALAPPDATA%` 側で書き換える経路を
持たないため、再配布物と実行時の内容が一致し、§15 の帰属が配布物のまま保たれる。

TIP はこのファイルを読まない。数万行の索引を in-proc TIP が抱えると、TIP をロードする
アプリのプロセス数だけ常駐量が増える。索引は Host プロセスに 1 つだけ置く（§8.1）。

### 7.2 列定義

TSV は UTF-8（BOM なし）、改行は LF、区切りはタブ 1 文字とする。`#` で始まる行はコメントで、
先頭のコメント行群が §15.1 のヘッダを担う。

| 列 | 型 | 内容 |
|---|---|---|
| 1 `emoji` | UTF-8 文字列 | 絵文字の表層形。コードポイント列をそのまま保持する |
| 2 `readings` | `\|` 区切りの文字列 | 正規化済みのかな読みキー（§9.1）。空欄可 |
| 3 `triggers` | `\|` 区切りの文字列 | 正規化済みの `:trigger` キー（§9.1）。空欄可 |
| 4 `name_ja` | 文字列 | 候補窓に出す和名。注釈として使う（§4） |
| 5 `rank` | 符号なし整数 | 大きいほど優先。同順位は §9.4 の規則で決まる |

列と要素の関係は次のとおりとする。`readings` と `triggers` は**多値列**であり、1 個以上の要素を
`|`（U+007C）で連結した文字列を値に持つ。`emoji`、`name_ja`、`rank` は**単値列**であり、要素は
1 個だけである。

- どの列でも、要素にタブ、`|`、改行を含めない。`|` は多値列の区切りとしてだけ現れる。
- 単値列の値に `|` を含めない。
- 多値列に空の要素を置かない。先頭と末尾の `|`、および `||` は不正とする。列全体が空欄
  （要素 0 個）であることは許す。
- 多値列の要素は重複させない。

`readings` と `triggers` の両方が空欄の行は検索に到達しないため、ビルド時に落とす。

### 7.3 再ポートの規則

データは Mozc `emoji_data.tsv`（BSD-3-Clause、© Google）と Unicode CLDR の絵文字注釈から
再ポートする。原典を逐語コピーせず、porter スクリプトで本形式へ変換する（§15.2）。

`emoji` 列にはいかなる Unicode 正規化も適用しない。異体字セレクタ（U+FE0F）や ZWJ シーケンス
は原典のまま保つ。正規化すると別の絵文字になったり、カラー表示が落ちたりするためである。

肌色修飾子付きのシーケンスは、原典に単独の項目として存在する場合だけ取り込む。基底絵文字から
5 通りの修飾子付き異体を自動生成しない。生成すると行数が数倍になり、候補列も同義の異体で
埋まる。

描画できない絵文字を候補に出さないため、porter はビルド時に Emoji バージョンの上限で行を
絞る。上限値は §15.1 のヘッダに記録する。実行時のバージョン判定は行わない。判定を実行時に
置くと、同じデータから環境ごとに異なる候補列が出て、§16 の期待値表が書けなくなる。

## 8. Host 配信境界と IPC

### 8.1 責務境界

| 層 | 責務 |
|---|---|
| `core/` | 絵文字索引の構築、正規化（§9.1）、2 つの検索とランキング（§9.2、§9.3、§9.4）を純粋関数として持つ。ファイル I/O と IPC を持たない |
| `inference-host/` | TSV の読み込み、索引の常駐、`QueryCandidates` 応答への合流、`:trigger` 検索の応答 |
| `tsf-tip/` | `:trigger` モードの状態機械（§11）、注釈付き候補窓の描画（§10）、確定文字列の組み立て |

索引は `emojiRewriter` が有効になった最初の問い合わせで遅延ロードする。`UpdateConfig` で
`false` から `true` へ変わったときも同じ経路を通る。既定 OFF のまま使うユーザーは、この
ファイルを一度も読まない。

常駐量の目標は索引全体で 8 MB 以下とする。超える場合は実行時に切り詰めず、porter 側で
行数か列を削って収める。実行時に切り詰めると、環境によって候補列が変わる。

### 8.2 `CandidateField.description`

`ipc::CandidateField` に `description`（文字列、既定は空）を追加する。Host 側データ駆動
リライタの注釈はこの欄で伝送する。

これは欄の追加であり、`kEnvelopeVersion` は上げない（`ipc/include/azookey/ipc/Messages.h` の
wire generation 規約に従う）。旧 Host と新 TIP の組み合わせでは欄が欠けて空文字列になり、
候補は表層形だけで表示される（§10.4 と同じ劣化）。

`core::CandidateSource` に `Emoji` を追加し、wire 表現は `"emoji"` とする。TIP はこの値で
絵文字候補を識別し、学習観測から除外する（§12）。

### 8.3 かな読み引きの合流

かな読み引きは新しい MessageType を作らず、既存の `QueryCandidates` 応答に混ぜる。M62-C の
記号読み引きと同じ形であり、TIP 側の受信経路を増やさない。

Host は通常の候補生成を終えた後に絵文字候補を追加する。追加は末尾に対してのみ行い、既存
候補の順序と内容を変えない（§10.2）。件数の上限と `max_candidates` との適用順は §9.5 が定める。

### 8.4 `:trigger` 検索の要求

`QueryCandidatesRequest` に `emoji_trigger`（文字列、既定は空）を追加する。空でないとき、
その要求は `:trigger` 検索であり、次の契約に従う。

- `reading` は空でなければならない。空でない `reading` と空でない `emoji_trigger` が同時に
  来たとき、Host は候補を生成せず空の候補列（`partial == false`）で応答する。これは
  `QueryCandidatesRequest` の payload を解釈できなかったときと同じ応答であり、
  `QueryCandidatesResponse` には誤りを伝える欄が無いためこの形を採る。あわせて warning を
  ログへ出す。
- Host は変換器、Zenzai、リランカを起動しない。応答は絵文字候補だけで構成する。
- `left_context` は無視する。
- 応答の `partial` は常に `false` とする。表引きは分割して返す対象ではない。

新しい MessageType を足す設計も採り得たが、採らなかった。`emoji_trigger` を欄として足せば、
`RequestScheduler` のキャンセルと最新判定（`request_id` 単位）、TIP 側の応答ハンドラ、
候補窓への流し込みがそのまま再利用できる。新しい MessageType はこれらを一式作り直す一方、
得られるのは要求の型が分かれるという表現上の差だけである。かわりに、経路の分岐が欄の値に
依存する点を上の契約で明文化する。

`:trigger` 検索は索引を引くだけで、モデルのロックを取らない。推論の実行中でも応答できる。

### 8.5 古い応答の破棄

`Collecting` と `Listing` では打鍵ごとに問い合わせが飛ぶため、`sm` に対する応答が `smi` の
問い合わせより後に届くことがある。TIP は最新の検索語に対する応答だけを候補窓へ反映し、それ以外
は捨てる。判定には要求ごとの `request_id` を使う（Host 側の最新判定は
`RequestScheduler::MarkLatest` と `IsLatest`）。ライブ変換（M14）の staleness 処理と同じ形で
ある。

捨てた応答で候補窓の内容と状態（§11.2）を変えない。古い応答で窓を開くと、既に打ち終えた検索語
と一致しない候補列が出る。

## 9. 検索とランキング

### 9.1 正規化

検索キーは、データのビルド時と実行時の問い合わせで同一の規則を通す。実行時の実装は `core/` に
純粋関数として置く。ビルド時は porter が同じ規則を実装する（§15.2）。実装が 2 つに分かれるため、
porter の出力を実行時の関数へもう一度通しても変わらないこと（冪等性）を検証する（§16）。

かな読みキーの正規化手順は次のとおりである。

1. NFKC を適用する。
2. カタカナ（U+30A1〜U+30F6）をひらがな（U+3041〜U+3096）へ写す。
3. 空白文字を除去する。

長音記号（`ー`）と濁点半濁点は保つ。`らーめん` と `らめん` を同一視すると、無関係な読みに
絵文字が付く。

`:trigger` キーの正規化手順は次のとおりである。

1. ASCII 英字を小文字化する。
2. `[a-z0-9_+-]` 以外の文字を除去する。

許可する文字集合は §11.2 で検索語を伸ばす打鍵の集合と一致させる。`+` を含めるのは `:+1:` の
ように `+` を持つ trigger があるためで、除去すると打鍵した検索語がキーと合わなくなる。

### 9.2 かな読み引き

読み全体が読みキーと**完全一致**したときだけ絵文字候補を出す。前方一致と部分一致は使わない。

前方一致を許すと、`わ` を打った時点で読みが `わ` で始まる全絵文字が候補列へ流れ込み、通常の
変換候補が押し出される。かな読み引きは変換の邪魔をしない範囲でだけ働く。

読みが 32 文字を超えるときは索引を引かない。絵文字の読みがその長さになることはない。

かな読み引きの候補数上限は 4 件とする。これは設定ではなく仕様上の定数であり、通常の変換候補を
候補窓の 1 ページから押し出さないための上限である。

### 9.3 `:trigger` 曖昧検索

検索語は 3 つの一致クラスのいずれかで trigger キーに一致する。

- **Exact**：正規化済みの検索語が trigger キーと完全一致する。
- **Prefix**：trigger キーが検索語で始まる。
- **Subsequence**：検索語の各文字が、その順序で trigger キーに現れる。

検索語が 1 文字のときは Exact と Prefix だけを評価する。1 文字の Subsequence は数千件に
一致し、順序規則を通しても意味のある上位が残らない。

検索語が 32 文字を超えるときは索引を引かず、空の候補列を返す。

編集距離による補正は行わない。`:smle` は `:smile` に一致しない。補正を入れると、一致クラスの
優先順位と補正コストを混ぜた順序になり、§16 の期待値表が保てなくなる。

候補数上限は `emojiMaxCandidates`（既定 12）とする。既存の `QueryCandidatesRequest.max_candidates`
との関係は §9.5 が定める。

### 9.4 順序規則

候補列は次のキーの辞書式順序で昇順に並べる。すべて決定的であり、同点は残らない。

1. 一致クラス（Exact = 0、Prefix = 1、Subsequence = 2）。
2. 一致した trigger キーの長さ（短い順）。検索語 `smi` に対して `smile` が `smiley` より
   前に出る。
3. `rank`（大きい順）。
4. trigger キーのコードポイント列（昇順）。
5. `emoji` のコードポイント列（昇順）。

1 つの絵文字が複数の trigger キーに一致することがある。並べ替えの前に、絵文字ごとに上記の
キーで最小となる一致（一致クラスと trigger キーの組）を代表として選び、絵文字単位に重複を除く。
代表の選択と候補列の並べ替えで同じキーを使うため、順序の決め方は 1 つで済む。

かな読み引きは一致クラスが Exact に固定されるため、実質は `rank` の降順、次いで `emoji` の
コードポイント列の昇順で決まる。

上限件数の適用は並べ替えの後に行う。

### 9.5 `max_candidates` との関係

`QueryCandidatesRequest.max_candidates`（既定 10）は、Host が応答全体を切り詰める既存の上限で
ある（`Dispatcher::HandleQueryCandidates`）。§9.2 と §9.3 の絵文字側の上限はこれとは別の値
なので、両者の適用順を定める。

**`:trigger` 検索**では、TIP が `emojiMaxCandidates` の値をそのまま `max_candidates` に入れて
要求する。Host は既存の切り詰めを行うだけで、絵文字専用の二重の上限を持たない。切り詰めが 1 か所
に留まり、`Dispatcher` に `:trigger` 用の分岐が増えない。設定の更新が TIP と Host で前後した場合
も、要求に入った値が効くため応答件数が一意に決まる。

**かな読み引き**では、Host は次の順で応答を組み立てる。

1. 絵文字候補を §9.2 の上限（4 件）まで選ぶ。件数を `k` とする。
2. 絵文字以外の候補が 1 件以上あるとき、`k` を `max_candidates - 1` で頭打ちにする。変換候補を
   必ず 1 件は残すためである。
3. 絵文字以外の候補を `max_candidates - k` 件へ切り詰める。
4. 切り詰めた列の末尾へ絵文字候補を足す。

`max_candidates == 0` は既存実装で「切り詰めなし」を意味するため、この場合は手順 2 と手順 3 を
行わず、絵文字は §9.2 の 4 件だけを上限とする。

切り詰めを絵文字の追加より**前**に行うのは、後から切り詰めると末尾の絵文字が最初に落ち、
`emojiRewriter` を有効にしても絵文字が一度も見えない場合が生じるためである。

この手順は、変換候補の表示数を `emojiRewriter` の値によって減らす。これを避けるため、TIP は
`emojiRewriter == true` のとき、通常送る `max_candidates` に §9.2 の上限（4）を足した値を要求に
入れる。結果として、変換候補は `emojiRewriter` の値によらず同じ件数だけ残り、絵文字はその後ろに
最大 4 件付く。応答の総数が要求した `max_candidates` を超えることはない。

記号候補（M62-C）が同時に有効なときの手順は §19.5 が定める。

## 10. 候補窓 UX

### 10.1 注釈付き view-model

現在の `CandidateWindow::Show` は `std::vector<std::wstring>` を受け取り、表層形だけを描く。
これを、表層形と注釈の 2 欄を持つ要素の列へ拡張する。

```cpp
struct CandidateViewItem {
  std::wstring surface;      // 確定に使う文字列
  std::wstring description;  // 注釈。空可。確定文字列には入らない
};
```

描画は表層形の欄と注釈の欄を横に並べ、注釈は副次色で描く（色は `docs/native-ui-spec.md` §1.3）。
表層形の欄幅はページ内の最大幅に合わせ、上限で頭打ちにする。注釈が欄幅を超えるときは末尾を
`…` で省略する。

絵文字の表層形はカラーフォントで描く。描画方法は `docs/native-ui-spec.md` §3.4 が正典であり、
本書は指定しない。

注釈は表示専用である。確定、学習観測、`ITfCandidateListUIElement` のいずれにも注釈を
連結しない。

TIP ローカル候補を選んだ確定では `CommitObservation` を送らない。
Host 候補を選んだ確定でも、TIP ローカル候補は `shown` から除外してから観測を送る。

### 10.2 かな読み引きの候補列と確定動線

絵文字候補は、絵文字以外のすべての候補の**後ろ**に置く。絵文字候補どうしの相対順序は §9.4 の
とおりとする。

スコアで通常候補と混ぜない。混ぜると、同じ読みでも学習やモデルの状態によって絵文字の位置が
変わり、第 1 候補を奪う場合が出る。末尾固定なら、Space で候補窓を開いて Enter を押す既定の
動線は `emojiRewriter` の値によらず同じ結果になる。

選択と確定の操作は M5 の候補窓と同じである（↑ / ↓ で移動、数字キーで直接選択、クリックで
確定、Esc で取り消し）。絵文字候補のための専用キーは足さない。

確定すると `emoji` 列の文字列だけがアプリへ入る。注釈は入らない。

### 10.3 ライブ変換と予測候補との境界

`liveConversion == true` のとき、絵文字候補を preedit へ出さない。ライブ変換の最良候補の
選択対象から絵文字を除外する。読みを打っている途中で preedit が絵文字へ置き換わると、以降の
打鍵が何に対して効くのかが読み取れなくなる。

予測候補ウィンドウ（M15）にも絵文字候補を出さない。予測候補は Tab で第一候補を受理する動線
であり、絵文字が先頭に来ると誤受理の危険がある。

`:trigger` モードでは M5 の候補窓を使う。予測候補ウィンドウは使わない。`:trigger` の操作は
「一覧から選んで確定する」であって「第一候補を受理する」ではないためである。したがって
`:trigger` モードの候補窓は `predictionEnabled == false` でも開く。

一括変換（M58）と再変換（M20）の経路にも絵文字候補を出さない。どちらも読み全体を文へ変換
する経路であり、末尾に絵文字を足す意味がない。

### 10.4 UI-less モードと統合候補リストでの劣化

UI-less モードとアプリ描画ホストでは、候補は `ITfCandidateListUIElement::GetString` が返す
文字列としてアプリ側または OS 側に描かれる。この経路に注釈を載せる欄はない。

この経路では**表層形だけ**を返し、注釈は落とす。`surface + " " + description` のような連結を
行わない。統合インライン検索（M21、`ITfIntegratableCandidateListUIElement`）は返した文字列を
そのまま検索語として扱うため、連結すると注釈が検索語に混入する。

注釈が落ちても候補の順序と確定文字列は変わらない。劣化するのは注釈の表示だけである。

## 11. `:trigger` モードの状態機械

### 11.1 入口の条件と記号横取りの例外

状態は `Inactive`、`Collecting`、`Listing` の 3 つとする。`Inactive` 以外へ入るのは、次の
3 条件がすべて成り立つときに限る。

- `emojiRewriter == true` かつ `emojiTriggerSearch == true`。
- `inputMode == "hiragana"`。
- composition が空である。

`:` は `VK_OEM_1` として届き、キーボードレイアウトによって生成文字が変わる。`ToUnicodeEx` で
生成文字へ写してから ASCII の `:` かどうかを判定する（`TranslateOemCompositionSymbol` と同じ
手法）。

ここには既存方針の例外がある。TIP は現在、記号キーを composition 中だけ取り込み、composition が
無いときはアプリへ通す（`tsf-tip/src/TextService.cpp` の OEM 記号の扱い）。`:trigger` は
composition が無い状態から `:` を取り込んで composition を始めるため、この方針を破る唯一の入口に
なる。破らずに済ませる方法は無い。`:smile` にはかな読みが無く、composition を先に開く手段が
`:` の打鍵以外にないためである。

例外の影響は 3 つの条件で抑える。第一に、既定 OFF の `emojiRewriter` と `inputMode == "hiragana"`
の二重ゲートにより、英数モードのパススルーは一切変わらない。`http://` のように英数モードで打つ
文字列は影響を受けない。第二に、検索語の文字集合に当たらない打鍵で即座に `Inactive` へ戻り、
打った文字はそのまま残る（§11.2）。第三に、preedit には打鍵したとおりの文字列しか出さないため、
モードに入ったこと自体がテキストを変えない。

### 11.2 遷移表

| 現状態 | 入力 | 次状態 | 動作 |
|---|---|---|---|
| Inactive | `:` の打鍵、かつ §11.1 の条件を満たす | Collecting | `:` を composing 文字列として表示する |
| Inactive | `:` の打鍵、かつ §11.1 の条件を満たさない | Inactive | 従来どおりに扱う（composition が無ければアプリへ通す） |
| Collecting | `[A-Za-z0-9_+-]` の打鍵 | Collecting または Listing | 検索語へ 1 文字追加し、`emojiTriggerMinQueryLength` に達したら Host へ問い合わせる |
| Collecting | 上記以外の文字（`:` と空白を含む） | Inactive | `:` と検索語を composing 文字列として残したままモードを抜け、打鍵文字を通常入力として処理する |
| Collecting | Backspace | Collecting または Inactive | 検索語を 1 文字削る。`:` まで消えたら composition が空になり Inactive へ戻る |
| Collecting | Esc | Inactive | 候補窓は既に閉じている。`:` と検索語を composing 文字列として残したままモードを抜ける |
| Collecting | 応答が 1 件以上 | Listing | 候補窓を開く |
| Listing | ↑ / ↓ / Space | Listing | 選択を移動する |
| Listing | `[A-Za-z0-9_+-]` の打鍵 | Collecting または Listing | 検索語を伸ばして引き直す。0 件なら Collecting へ戻り候補窓を閉じる |
| Listing | Backspace | Collecting または Listing | 検索語を縮めて引き直す |
| Listing | Enter、クリック、`:` の打鍵 | Inactive | 選択中の絵文字で `:` から検索語末尾までを置き換えて確定する |
| Listing | Esc | Collecting | 候補窓を閉じ、`:` と検索語を composing 文字列として残す |

`Listing` での `:` を確定に割り当てるのは、`:smile:` と閉じ `:` まで打ち切る Slack の操作を
そのまま受けるためである。候補窓が開いていない `Collecting` では確定対象が無いため、同じ `:` は
リテラルとして扱う。

**`:trigger` モードでは数字キーによる直接選択を使わない。** 数字は常に検索語を伸ばす打鍵として
扱う。`:100` や `:+1` のように数字を含む trigger があるため、数字を確定へ割り当てると、候補窓が
開いた後にそれらの検索語を打ち切れなくなる。検索語の入力は代わりの手段が無いのに対し、選択と
確定は ↑ / ↓ / Space と Enter とクリックで足りる。修飾キー付きの直接選択（Ctrl + 数字など）も
採らない。アプリ側のショートカットと衝突しうるうえ、`:trigger` の候補は既定 12 件で、番号を
読んで押すより上下移動のほうが短いことが多い。

これは M5 の候補窓の既定操作との差である。かな読み引き（§10.2）を含む通常の候補窓では、数字
キーの直接選択はこれまでどおり働く。差が出るのは `:trigger` モードの `Listing` に限る。

`Collecting` と `Listing` の間、composing 文字列は打鍵したとおりの `:query` を保つ。選択中の
絵文字を preedit へ先行表示しない（§10.3 と同じ理由）。

確定は検索語の直前の `:` を含めて置換する。`:smile` を選んで確定すると、アプリへ入るのは
`😄` だけであり、`:` も検索語も残らない。

Esc は段階的に効く。候補窓が開いているとき（`Listing`）は窓を閉じるだけで、検索語は composing
文字列として残る。窓が閉じた状態（`Collecting`）の Esc はモードを抜け、`:` と検索語を composing
文字列として残す。以降の Esc は通常の composition 取り消しとして働く。1 打で composition ごと
消さないのは、打った検索語を直して引き直す動線を残すためである。

`emojiTriggerSearch == false` のとき、`:` は常に従来どおりに扱う。

## 12. 確定時の学習データの扱い

絵文字候補の確定は、学習ストアへ書かない。かな読み引きと `:trigger` 検索のどちらも同じである。

理由は 3 つある。第一に、`:trigger` 検索には読みが存在しない。`LearningStore` は読みをキーに
持つため、`:smile` のような検索語をキーとして書くと、かな読みの名前空間に別種のキーが混ざる。
第二に、絵文字の順位はデータの `rank` と §9.4 の順序規則だけで決まると定めており（§6）、学習に
よる並べ替えを入れると 2 つの順序決定が同じ候補列に同居する。第三に、絵文字の選択は入力の
表現そのものであり、学習ストアへ残す既定の対象としては踏み込みが大きい。

加えて、通常の変換候補を確定したときの `CommitObservation` から、絵文字候補を除外する。
`shown` 配列に絵文字候補を載せない。`shown` は負例学習（`ObserveCorrection`）の入力であり、
末尾に並んだだけの絵文字が「選ばれなかった候補」として記録されると、絵文字と無関係な読みの
スコアに影響しうる。除外の判定には `source == "emoji"` を使う（§8.2）。

絵文字の使用頻度を反映する仕組み（MRU など）は本書の対象外とする。導入する場合は、学習ストア
とは別の永続化と別のキー空間を定義したうえで、本節を改訂する。

## 13. 設定キー

`settings/mvp-settings.schema.json` へ次を追加する。

| キー | 型 | 既定 | 説明 |
|---|---|---|---|
| `emojiRewriter` | boolean | `false` | M62-D の絵文字リライター全体の有効化。`false` で §14 の不変条件が成り立つ |
| `emojiTriggerSearch` | boolean | `true` | `:trigger` 曖昧検索の有効化。`emojiRewriter == false` のときは無視される。有効でも `inputMode == "hiragana"` のときだけ働く（§11.1） |
| `emojiMaxCandidates` | integer | `12` | `:trigger` 検索の候補数上限。範囲は 1〜50。範囲外はクランプする |
| `emojiTriggerMinQueryLength` | integer | `1` | 候補窓を開くまでに必要な検索語の長さ。範囲は 1〜8 |
| `emojiDataPath` | string | `""` | 絵文字 TSV のパス。空のとき §7.1 の既定パスを使う |

かな読み引きの候補数上限は設定にしない（§9.2）。

## 14. フォールバックと既定 OFF の不変条件

`emojiRewriter == false` のとき、次が成り立つ。

- Host は絵文字 TSV を読まず、索引を構築しない。
- `QueryCandidates` の応答に `source == "emoji"` の候補が現れない。
- TIP は `:trigger` モードへ入らず、`:` の打鍵は従来どおり（composition が無ければアプリへ
  パススルー）に扱われる。
- 候補列、確定文字列、学習データが `emojiRewriter` 導入前と一致する。

データの読み込みに失敗したとき（ファイル不在、パーミッション、パース不能）、機能だけを無効化
して他の候補生成を続ける。失敗は warning を 1 回だけログへ出し、以後の問い合わせでは再試行
しない。再試行を毎回行うと、ファイルが無い環境で打鍵ごとにログが増える。

行単位の不正（§7.2 の文法に合わない行。列数不足、要素へのタブの混入、単値列の `|`、空要素など）
は当該行を落として読み込みを続ける。落とした行数を warning に含める。1 行の不正で索引全体を
失わせない。porter の verify（§15.2）は同じ文法を全行に対して事前に強制するため、正規に生成した
データでこの経路へ入ることはない。

読み込みに失敗した状態で `:trigger` モードへ入った場合、候補は 0 件となり §11.2 の
`Collecting` に留まる。`:` と検索語は composing 文字列として残るため、打った文字は失われない。

## 15. ライセンスと帰属

適用する規約は `docs/licensing-policy.md` の三層 attribution モデルである。本節はその 3 層を
絵文字データに対して具体化するだけであり、モデル自体を再定義しない。

### 15.1 ファイルヘッダ

`emoji.tsv` の先頭コメント行に次を記す。

- 由来元（Mozc `emoji_data.tsv` と参照した revision、Unicode CLDR とそのバージョン）。
- 各由来元のライセンス（Mozc は BSD-3-Clause © Google、CLDR は Unicode License v3）。
- ルート `THIRD_PARTY_LICENSES` への参照。
- porter のバージョンと、§7.3 で適用した Emoji バージョン上限。

### 15.2 porter スクリプト

再ポートは `scripts/emoji_porter.py` が行う。原典から本形式への変換手順をスクリプトとして
残すことが、`docs/licensing-policy.md` の再生成注記の要件を満たす。

porter は決定的でなければならない。固定した原典バージョンからは、常に同一バイトの
`emoji.tsv` が出る。出力行は `emoji` のコードポイント列で昇順に整列し、多値フィールド内の
要素も昇順に整列する。ハッシュ順や辞書の反復順に依存する箇所を残さない。

porter は出力前に verify を行い、§7.2 の文法を満たさない入力を失敗として扱う（部分的な出力を
残さない）。検査項目は次のとおりである。

- 列数がすべての行で 5 である。
- どの列の要素にもタブと改行が含まれない。
- 単値列（`emoji`、`name_ja`、`rank`）の値に `|` が含まれない。
- 多値列（`readings`、`triggers`）に空の要素が無い（先頭と末尾の `|`、`||` を含む）。
- 多値列の要素に重複が無い。
- `emoji` 列に重複が無い。
- `rank` が符号なし整数として解釈できる。

多値列の区切りとしての `|` は当然に許す。ここで弾くのは、区切りとして解釈できない位置の `|` と、
空要素だけである。

### 15.3 集約ファイル

ルート `THIRD_PARTY_LICENSES` に次の節を持つ。

- Mozc: SPDX `BSD-3-Clause`、原著作権表記、全文（第 3 条項を含む）、格納パス、派生である旨。
- Unicode CLDR: SPDX `Unicode-3.0`、出典バージョン、Unicode 表記、格納パス、派生である旨。

### 15.4 逐語コピーの禁止

原典のファイルをそのまま同梱しない。`emoji` と `name_ja` は原典に由来する派生データであり、
帰属を保ったまま本形式へ変換して持つ。

## 16. テスト観点

M62-D の受け入れ条件（`plans/windows-port-roadmap.md` M62-D）に対応する検証は次で行う。
`core/` の純粋関数として書ける項目は、TSF と IPC とモデルを起動せずに検証する。

| 対象 | 検証内容 | 層 |
|---|---|---|
| 正規化（§9.1） | カタカナとひらがな、NFKC、空白除去、長音の保持。trigger キーの小文字化と記号除去（`+` `_` `-` の保持）。porter 出力に対する冪等性 | core |
| かな読み引き（§9.2） | 完全一致だけが当たること。前方一致で当たらないこと。32 文字超で引かないこと。上限 4 件 | core |
| `:trigger` 検索（§9.3） | 3 つの一致クラスの判定。1 文字検索で Subsequence が働かないこと。編集距離で当たらないこと | core |
| 順序規則（§9.4） | 固定の索引に対する期待値表。同一絵文字の重複除去。上限適用が並べ替えの後であること | core |
| 候補列の合流（§10.2） | 絵文字候補が末尾にのみ付き、既存候補の順序と内容が変わらないこと | core / host |
| 件数上限の適用順（§9.5） | `:trigger` で `max_candidates` に `emojiMaxCandidates` が入り応答がその件数で収まること。かな読み引きで切り詰めが絵文字追加より前に行われ、絵文字が落ちないこと。`emojiRewriter` の ON / OFF で変換候補の件数が変わらないこと。既定値（10 / 12 / 4）と非既定値（`emojiMaxCandidates` の下限 1 と上限 50、`max_candidates` が絵文字上限を下回る場合）の双方で確認する | host |
| IPC（§8.2、§8.4） | `description` の往復。`emoji_trigger` と `reading` の同時指定で空の候補列が返ること。`partial` が常に `false` であること | ipc / host |
| 古い応答の破棄（§8.5） | 検索語を伸ばした後に古い応答が届いても候補窓の内容と状態が変わらないこと | tsf-tip |
| 状態機械（§11） | §11.2 の全遷移。入口ゲート（英数モードと composition 中で `:` を取り込まないこと）。`Listing` で数字キーが検索語を伸ばし確定しないこと（`:100` を打ち切れること）。確定文字列に `:` と検索語が残らないこと。Esc の段階動作 | tsf-tip |
| 注釈の表示（§10.1） | view-model が注釈を保持すること。確定文字列に注釈が入らないこと | tsf-tip |
| UI-less 劣化（§10.4） | `GetString` が表層形だけを返し、連結が起きないこと | tsf-tip |
| 既定 OFF（§14） | `emojiRewriter == false` で候補、確定、学習が不変であること。`:` がリテラルであること | tsf-tip / host |
| フォールバック（§14） | ファイル不在で他の候補が壊れないこと。不正行が落ちて読み込みが続くこと。warning が 1 回であること | host |
| TSV 文法（§7.2、§15.2） | 多値列の `|` 区切りが verify を通ること。単値列の `|`、空要素、要素内のタブが弾かれること | scripts / host |
| 再ポート（§15.2） | 固定の原典サブセットから porter が同一バイトの出力を出すこと。出力を Host のローダで読み直して同じ索引になること | scripts / host |

再ポートの検証には原典の全量を使わない。テストに必要な行だけを含む固定サブセットをリポジトリへ
置き、その入出力で round-trip を確認する。

## 18. M62-B 半角カタカナリライター

本節は M62-B のうちカタカナ分を定める。英字分は M60 が受け持つ（§18.8）。

節番号が §17 の後に続くのは、`plans/windows-port-roadmap.md` と Linear が §6 から §17 を
番号で参照しているためである。既存節を改番せずに追加する。

### 18.1 対象と入力

M62-B の入力は変換対象の読みである。

Host が返した候補を入力にしない。読みは常にかなであり、候補には漢字が混じる。ロードマップ
M62-B の「純かな候補」は、読みが純かなであることを指す。

生成する候補は全角カタカナと半角カタカナである。

処理は `core/` の純粋関数として書き、TSF と IPC とモデルに依存しない。M62-A と同じ形であり、
TIP ローカルで無 IPC である。

「TIP ローカルで無 IPC」は候補生成についての性質である。`katakanaRewriter` の値そのものは
§18.7 の Handshake 経路で Host から TIP へ届く。設定の伝播まで無 IPC と読むと、core の関数と
schema だけを足して設定が常に実質 OFF のままになる。

M62-A は `IRewriter` と `RewriterChain` の抽象を導入していない（`core/` にあるのは
`NumberRewriter` 単体である）。M62-B も同じ粒度の関数を 1 つ追加する形で実装し、
リライターの抽象化は行わない。M62-C でも導入しない判断とその理由は §19.1 にある。

### 18.2 純かな判定

対象は、次の文字だけからなり、かつひらがなを 1 文字以上含む読みである。

- ひらがな（U+3041 から U+3096）
- 長音符 `ー`（U+30FC）

次は対象外とし、候補を返さない。

- 漢字が混じる読み（`愛してる`）
- ASCII、全角英数、記号、空白
- すでにカタカナである読み
- 濁点と半濁点の結合文字（U+3099、U+309A）
- 繰り返し記号 `ゝ`（U+309D）と `ゞ`（U+309E）
- 長音符だけの読み

結合文字を対象外にするのは、合成済みの `が`（U+304C）だけを扱って写像表を一意に保つため
である。`RomajiKanaConverter` は合成済みのかなを出すため、ローマ字入力の経路でこの分岐へは
入らない。

### 18.3 全角カタカナ

ひらがな 1 文字を、コードポイントに 0x60 を加えてカタカナへ写す。

`ー` はそのまま残す。

U+3041 から U+3096 のすべてに対応するカタカナ（U+30A1 から U+30F6）があるため、この写像が
途中で失敗することはない。

### 18.4 半角カタカナ

全角カタカナから半角カタカナへ写す。

清音、撥音、促音、小書きのかなは 1 コードポイントへ写す（`ア`→`ｱ`、`ッ`→`ｯ`、`ン`→`ﾝ`、
`ヲ`→`ｦ`）。

濁音と半濁音は 2 コードポイントへ分解する（`ガ`→`ｶﾞ`、`パ`→`ﾊﾟ`、`ヴ`→`ｳﾞ`）。

`ー` は `ｰ`（U+FF70）へ写す。

半角に対応する文字が無いかなが 1 文字でもあるとき、半角候補を生成しない。全角候補は生成する。
対応が無いのは `ゐ`、`ゑ`、`ゎ`、`ゕ`、`ゖ` の 5 文字である。

縮退を文字単位ではなく候補単位で行うのは、一部だけ全角が混じった文字列は幅が揃わず、確定
文字列として使えないためである。

### 18.5 候補列への注入

注入の規則は M62-A（§3）と同じである。

TIP は Host 候補を先に保ち、その末尾へカタカナ候補を追加する。

同じ表層形がすでに Host 候補または先行するリライター候補にある場合は追加しない。Host が
すでにカタカナ候補を返しているときは、この重複除去で全角カタカナ候補が落ちる。

一括変換、ライブ変換、予測候補の経路には追加しない。

順序は全角カタカナ、半角カタカナの順である。

数字リライターと同時に有効でも、同じ読みに両方の候補が付くことはない。読みは ASCII 十進
数字列と純かなのどちらか一方しか満たさないためである。両方が有効なときの生成順は数字、
カタカナの順とする。

カタカナ候補は `Candidate::reading` に入力の読みを、`source` に `CandidateSource::Heuristic`
を持つ。`debug_info` の接頭辞は `katakana-rewriter:` とする（M62-A の `number-rewriter:` に
揃える）。

### 18.6 注釈

各候補は `Candidate::description` に和文注釈を持つ（§4）。

M62-B で使う注釈は次のとおりである。

- `全角カタカナ`
- `半角カタカナ`

### 18.7 設定キー

`settings/mvp-settings.schema.json` へ次を追加する。

| キー | 型 | 既定 | 説明 |
|---|---|---|---|
| `katakanaRewriter` | boolean | `false` | M62-B: 純かなの読みから全角カタカナと半角カタカナの候補を注入する |

全角と半角を別のキーに分けない。片方だけを求める設定要求が現状無く、キーを 2 つにすると
§18.9 の不変条件を検証する組み合わせが 4 通りへ増える。

Host は runtime settings の値を Handshake 応答へ載せ、TIP は通常の変換候補を受信した後に
カタカナ候補をローカルで追加する。Handshake 応答に設定値がない旧 Host は `false` として
扱う（§3 の `numberRewriter` と同じ）。

キーの追加は schema だけでは完結しない。`settings/default-settings.sample.json` と
settings-app の許可キーを schema と同期し、Host の runtime settings、Handshake payload、
TIP の保持値まで `numberRewriter` と同じ経路を通す。変更対象の一覧は
`plans/windows-port-roadmap.md` M62-B にある。

### 18.8 英字分と M60 の境界

M62-B の英字分（幅と大小のバリアント）は本書で定めない。M60
（`docs/inline-english-candidate-spec.md`）が受け持つ。

M60 は生ローマ字バッファを素材に英単語候補を注入する経路をすでに持ち、幅と大小のバリアントは
その素材から作れる。TIP ローカルに 2 つ目の英字候補生成を置くと、同じ打鍵に対して 2 つの経路
が候補を注入し、順序と重複除去をどちらが決めるかが定まらない。

M60 側で確定した内容は同書 §3（素材の一覧）と §4.3（候補内の固定順）にある。半角の小文字、
半角の大文字、全角の小文字、全角の大文字の 4 バリアントは、同書の
`inlineEnglishCaseVariants` と `fullWidthEnglishCandidate` の組み合わせで生成する。

同書 §3 は、これらを生ローマ字そのものではなく `lower(r)` を基準に生成すると定める。生ローマ字は
Shift 併用打鍵を保持するため、`Apple` と打った場合に小文字形が出ず 4 形が崩れるのを防ぐ。

`katakanaRewriter` は英字に作用しない。

### 18.9 既定 OFF の不変条件

`katakanaRewriter == false` のとき、次が成り立つ。

- TIP は読みの純かな判定を行わない。
- 候補列にカタカナ候補が追加されない。
- 候補列、確定文字列、学習データが `katakanaRewriter` 導入前と一致する。

カタカナ候補は注釈を持つため、§2 の方針どおり IPC の候補表現へは流れない。確定時の
`CommitObservation` の `shown` に載らず、カタカナ候補そのものを確定したときは
`CommitObservation` を送らない。

### 18.10 テスト観点

M62-B の受け入れ条件（`plans/windows-port-roadmap.md` M62-B）に対応する検証は次で行う。

| 対象 | 検証内容 | 層 |
|---|---|---|
| 純かな判定（§18.2） | ひらがなと長音符だけの読みが対象になること。漢字混在（`愛してる`）、ASCII、記号混在、空文字列、長音符だけの読み、結合文字を含む読みが候補を返さないこと | core |
| 全角カタカナ（§18.3） | `あっぷる`→`アップル`。小書きかな、`ー`、`ゔ`、`ゖ` までの全域を写せること | core |
| 半角カタカナ（§18.4） | `あっぷる`→`ｱｯﾌﾟﾙ`。濁音と半濁音が 2 コードポイントへ分解されること。`ヲ` と `ー` の写像 | core |
| 半角の縮退（§18.4） | `ゐ`、`ゑ`、`ゎ`、`ゕ`、`ゖ` を含む読みで半角候補が出ず、全角候補は出ること | core |
| 注釈（§18.6） | 各候補が `全角カタカナ` / `半角カタカナ` を持つこと。確定文字列に注釈が入らないこと | core / tsf-tip |
| 重複除去（§18.5） | Host がカタカナ候補を返しているとき全角候補が重複しないこと。既存候補の順序と内容が変わらないこと | tsf-tip |
| 数字リライターとの併存（§18.5） | 両方 ON で `123` に数字候補だけ、`あっぷる` にカタカナ候補だけが付くこと | tsf-tip |
| 既定 OFF（§18.9） | `katakanaRewriter == false` で候補、確定、学習が不変であること | tsf-tip |

## 19. M62-C 記号リライター

本節は M62-C を定める。

節番号が §18 の後に続くのは、§6 から §17 を番号で参照している箇所を保つためである（§18 の冒頭と同じ理由）。

### 19.1 2 つの経路と責務境界

M62-C は次の 2 つの経路で記号候補を生成する。

- **かな読み引き**：変換対象の読みが記号の読みと一致するとき、記号候補を候補列の末尾へ追加する（`かぎかっこ` → `「」`）。データ駆動で、Host が持つ。
- **variant chain**：候補列にある記号と同じ族の記号を関連候補として追加する（`「` → `『【〔（`）。小さな固定表で、TIP ローカルに持つ。

2 つは合成して働く。読み引きが族の代表を候補列へ置き、chain がその族を広げる。

chain の入口を候補の表層形に置くのは、記号だけからなる読みが通常の打鍵では発生しないためである。
TIP は記号キーを composition 中だけ取り込み、composition が無いときはアプリへ通す（§11.1 が
`:` の例外を論じるときに挙げた既存方針）。
読みを入口にすると、chain は `「` を単独で読みへ入れる手段がないまま、事実上発火しない。

責務の分担は次のとおりとする。

| 層 | 責務 |
|---|---|
| `core/` | 記号索引の構築、読みキーの正規化（§9.1 と同一）、読み引きとその順序付け（§19.3）、chain 表と展開（§19.4）を純粋関数として持つ。ファイル I/O と IPC を持たない |
| `inference-host/` | TSV の読み込み、索引の常駐、`QueryCandidates` 応答への合流（§19.5） |
| `tsf-tip/` | chain 展開関数の呼び出しと候補列への追加、注釈付き候補窓の描画（§10.1）、確定文字列の組み立て |

索引の遅延ロードと常駐の扱いは §8.1 と同じである。
記号データは絵文字データより 1 桁小さいが、Host に置く判断は変えない。TIP は読み引きの索引を持たない。

M62-A と M62-B が見送った `IRewriter` と `RewriterChain` の抽象は、M62-C でも導入しない（§18.1 の保留はここで解消する）。
数字とカタカナのリライターは読みを入力に取り、chain は候補列を入力に取る。共通のインターフェースは両方の入力を受ける形になり、
実装の分岐は残ったままインターフェースだけが増える。
かわりに TIP の注入順を数字、カタカナ、記号 chain の順に固定し、重複除去は先に入った候補を残す（§3）。

### 19.2 記号データの形式と再ポート

記号データは `inference-host` が読む単一の TSV ファイルである。
既定パスは Host の実行ファイルと同階層の `data/symbol.tsv` とし、`symbolDataPath` で上書きできる（§19.8）。
供給と読み取り専用資産としての扱い、ホットリロードを持たないこと、TIP が読まないことは §7.1 と同じである。

TSV の文法は §7.2 が定めるものをそのまま使う。
UTF-8（BOM なし）、LF、タブ 1 文字区切り、`#` で始まるコメント行、多値列を `|` で連結する規則、単値列と多値列に対する制約は共通である。
列の定義だけを次のとおり別に持つ。

| 列 | 型 | 内容 |
|---|---|---|
| 1 `symbol` | UTF-8 文字列 | 記号の表層形。`（` のような 1 文字と `（）` のような複数文字の両方を取る |
| 2 `readings` | `\|` 区切りの文字列 | 正規化済みのかな読みキー（§9.1）。1 個以上 |
| 3 `name_ja` | 文字列 | 候補窓に出す和名。注釈として使う（§19.6） |
| 4 `rank` | 符号なし整数 | 大きいほど優先。同順位は §19.3 の規則で決まる |

絵文字の `triggers` に当たる列は持たない。`:trigger` 検索は M62-D 専用である。

`readings` が空になる行はビルド時に落とす。読み引き以外の入口を持たないためである。

データは Mozc `symbol.tsv`（BSD-3-Clause、© Google）から再ポートする。
原典を逐語コピーせず、`scripts/symbol_porter.py` が本形式へ変換する。
porter の決定性と verify の要件は §15.2 と同じであり、検査項目は列数を 4 に読み替えたうえで同じ規則を適用する。
verify の実装は絵文字 porter と共有し、文法の解釈が 2 つに分かれないようにする。

原典の列は役割で読む。行によって末尾の列が欠けるため、列数を固定して解釈しない。
原典の列は POS、記号、読み（空白区切り）、説明、追加説明、カテゴリ、メモ、Unicode 名の順に並ぶ。
参照した revision は §19.11 のヘッダに記録する。

各列は次の規則で作る。

- `symbol` は原典の記号列をそのまま取る。Unicode 正規化を適用しない（§7.3 と同じ理由）。
- `readings` は原典の読み列を空白で分割し、§9.1 のかな読みキーの正規化を通し、ひらがなと長音符だけからなるものを残す。
- `name_ja` は原典の説明列を取る。説明列が空の行は落とす。
- `rank` は原典の行順から導く。原典に順位の列がないためである。有効行を上から数え、先頭ほど大きい値を与える。他の列に依存させない。

読み列から ASCII と記号の読みを落とすのは、原典がその欄で記号どうしの関連候補を表現しているためである。
原典では `（` の読みに `[` `「` `(` `｢` が並び、`「` を読みとして引くと括弧の族が返る。
azooKey ではこの役割を chain（§19.4）が担うため、読み引きの入口はかなだけにする。
ASCII の読みを残すと、英数字の入力に記号候補が混ざる。

出力の整列は §15.2 と同じく `symbol` のコードポイント列で昇順、多値列の要素も昇順とする。
`symbol` が重複する行を検出したら porter は失敗する。原典では記号列が一意であり、重複は再ポートの誤りを意味する。

### 19.3 かな読み引き

読み全体が読みキーと完全一致したときだけ記号候補を出す。
前方一致と部分一致は使わない（§9.2 と同じ理由）。

読みキーの正規化は §9.1 のかな読みキーの規則をそのまま使う。実行時とビルド時で同一の規則を通すこと、冪等性を検証することも同じである。

読みが 32 文字を超えるときは索引を引かない。

候補数の上限は 4 件とする。設定にしない。
`かっこ` のように十数個の記号が並ぶ読みがあるため、この上限は族の全体を返さない。
族の残りは chain が候補列へ足すため、読み引きは代表だけを返せば足りる。

順序は `rank` の降順、次いで `symbol` のコードポイント列の昇順とする。
一致は完全一致に固定されるため、§9.4 の一致クラスと一致キー長は効かない。

### 19.4 variant chain

chain 表は `core/` にコード内の固定表として持つ（`core/src/SymbolChainTable.cpp`）。
Mozc 由来データから生成しない。

コード内に持つ判断には 3 つの理由がある。
第一に、TIP に読み引きの索引を抱えさせない分割（§19.1）を保ったまま、chain だけを in-proc で引ける。
第二に、原典のカテゴリ列から族を導くと、TIP 側のソースにも Mozc の帰属が生じる。括弧の族は Unicode の定義と
`docs/bracket-pairing-spec.md` §4.1 の対応表から自前に書ける（§19.11）。
第三に、chain の並び順は候補窓での見やすさで決めるものであり、原典の行順とは別の判断である。

表は順序付きの文字列の列（族）の集まりとする。各要素は表層形と和名の対を持つ。

- 1 つの表層形は高々 1 つの族に属する。
- 族は表層形の綴りを混ぜない。開き括弧の族には `「` のような 1 文字だけを、括弧対の族には `「」` のような対だけを置く。
- 初版が持つ族は開き括弧、閉じ括弧、括弧対の 3 つとする。矢印や罫線の族を足す場合は表への追加だけで済み、以下の展開規則は変わらない。

展開は次のとおりとする。

1. 候補列のうち、表層形が chain 表の要素と完全一致する候補を探す。
2. 該当する候補が複数あるときは最上位の 1 件だけを種とする。
3. 種が属する族から種を除いた全要素を、族の定義順で候補列の末尾へ足す。種そのものは候補列の元の
   位置に残り、末尾へは複製しない。

族の順序を固定し、種の位置から回して並べ替えない。
回すと、同じ読みでも候補列のどれが種になったかで並びが変わる。

族の要素数は構成上 12 以下であり、展開に別の上限を設けない。
種を 1 件に絞るのは、異なる族の種が 2 件並んだときに候補列が族 2 つ分伸びるのを避けるためである。

すでに候補列にある表層形は追加しない（§3 の重複除去）。
読み引きが `「」` と `『』` を返した後で括弧対の族を展開すると、この重複除去で `『』` が落ちる。

種の判定には表層形だけを使い、候補の `source` を見ない。
記号は読み引き以外にシステム辞書からも返るため、`source` で絞ると同じ表層形が経路によって展開されたりされなかったりする。

### 19.5 候補列への合流と件数上限

読み引きの結果は新しい MessageType を作らず、既存の `QueryCandidates` 応答に混ぜる（§8.3）。
Host は通常の候補生成を終えた後に記号候補を追加し、既存候補の順序と内容を変えない。

記号候補は通常の候補の後ろ、絵文字候補の前に置く。
記号は読みと 1 対 1 に近い対応を持ち、変換候補の代わりになりやすいためである。

`emojiRewriter` と同時に有効なとき、§9.5 のかな読み引きの手順は 2 つの末尾へ次のように一般化する。

1. 記号候補を §19.3 の上限（4 件）まで、絵文字候補を §9.2 の上限（4 件）まで選ぶ。件数の合計を `k` とする。
2. どちらでもない候補が 1 件以上あるとき、`k` を `max_candidates - 1` で頭打ちにする。超過分は絵文字候補から先に落とす。
3. どちらでもない候補を `max_candidates - k` 件へ切り詰める。
4. 切り詰めた列の末尾へ、記号候補、絵文字候補の順で足す。

`max_candidates == 0` のとき手順 2 と手順 3 を行わないことは §9.5 と同じである。

TIP は有効なリライターごとに上限 4 を要求値へ足す。
`symbolRewriter` と `emojiRewriter` の両方が有効なら、通常送る `max_candidates` に 8 を足して要求する。
変換候補の件数がリライターの設定値によって変わらないという §9.5 の性質を、2 つの末尾に対しても保つためである。

chain 候補は TIP ローカルに追加するため `max_candidates` の対象外である。
TIP は Host 応答を受け取った後に、§19.4 の展開を候補列へ適用する。

一括変換、ライブ変換、予測候補、再変換の経路には記号候補を追加しない（§10.3 と同じ）。

### 19.6 注釈

各候補は `Candidate::description` に和文注釈を持つ（§4）。

読み引き由来の候補は `name_ja` を注釈に使う（`始めかぎ括弧`、`丸括弧` など）。
注釈は §8.2 の `CandidateField.description` で伝送する。この欄の定義と互換性の扱いは M62-D と共用し、
M62-C と M62-D のどちらを先に実装しても同じ欄を使う。

chain 由来の候補は chain 表が持つ和名を注釈に使う。
TIP は読み引きの索引を持たないため、表側に和名を並べて置く。

`Candidate::reading` には入力の読みを入れる。
`source` は読み引き由来と chain 由来のどちらも `CandidateSource::Symbol` とし、wire 表現は `"symbol"`
とする（`SourceToWire` へ追加する）。
`debug_info` の接頭辞は `symbol-rewriter:` とする。

### 19.7 学習データの扱い

記号候補の確定は、読み引き由来と chain 由来のどちらも学習ストアへ書かない。
通常の候補を確定したときの `CommitObservation` の `shown` にも記号候補を載せない。
記号候補そのものを確定したときは `CommitObservation` を送らない。
除外の判定には `source == "symbol"` を使う。

理由は §12 の絵文字とは異なる。記号候補は読みを持ち、`LearningStore` のキー空間と衝突しない。
それでも学習の対象から外すのは、2 つの経路のうち chain 側が TIP ローカルで、観測を送る経路そのものを持たないためである（§2）。
片方だけを学習に載せると、同じ記号が読み引きで出たか chain で出たかによって以後の順位が変わる。

使用頻度を反映する仕組みは §12 と同じく本書の対象外とする。

### 19.8 設定キー

`settings/mvp-settings.schema.json` へ次を追加する。

| キー | 型 | 既定 | 説明 |
|---|---|---|---|
| `symbolRewriter` | boolean | `false` | M62-C: かな読み引きと variant chain の両方の有効化 |
| `symbolDataPath` | string | `""` | 記号 TSV のパス。空のとき §19.2 の既定パスを使う |

読み引きと chain を別のキーに分けない。
2 つは合成して働き（§19.1）、読み引きだけを有効にすると族が代表 4 件で切れ、chain だけを有効にすると種を出す経路がシステム辞書に限られる。
片方だけを求める設定要求が想定できないうえ、キーを 2 つにすると §19.10 の不変条件を検証する組み合わせが 4 通りへ増える（§18.7 と同じ判断）。

キーの伝播経路は §18.7 と同じである。
schema、`settings/default-settings.sample.json`、settings-app の許可キー、Host の runtime
settings、Handshake 応答、TIP の保持値まで `numberRewriter` と同じ範囲を通す。
TIP は chain の展開に `symbolRewriter` の値を必要とするため、Host 側だけに値が届いた状態では機能が半分しか働かない。
Handshake 応答に設定値がない旧 Host は `false` として扱う。

### 19.9 M61 自動カッコペアリングとの境界

M61 は打鍵に反応する機能であり、M62-C は候補列に対する機能である。
候補窓から `「」` を選んで確定しても、確定は commit 経路（`SetText`）を通るためペアリングは発火しない。
逆に `bracketPairing == true` で `「` を打鍵しても、composition が空なら文書へ直接入り、M62-C の入口にはならない。
両方を有効にしても互いの挙動を変えない。

chain 表と M61 の組み込みカッコ対応表は別の表である。
前者は候補の族を、後者は開きと閉じの対応を定める。
括弧対の族の綴りは `docs/bracket-pairing-spec.md` §4.1 の対応表と矛盾しないものにし、両者の一致をテストで突き合わせる（§19.12）。

### 19.10 フォールバックと既定 OFF の不変条件

`symbolRewriter == false` のとき、次が成り立つ。

- Host は記号 TSV を読まず、索引を構築しない。
- `QueryCandidates` の応答に `source == "symbol"` の候補が現れない。
- TIP は chain 表を引かず、候補列に関連候補が追加されない。
- 候補列、確定文字列、学習データが `symbolRewriter` 導入前と一致する。

データの読み込みに失敗したとき（ファイル不在、パーミッション、パース不能）、読み引きだけを無効化して他の候補生成を続ける。
失敗は warning を 1 回だけログへ出し、以後の問い合わせでは再試行しない（§14 と同じ）。

chain はコード内の固定表を引くため、データの読み込み結果に依存しない。
記号 TSV が無い環境でも、システム辞書が返した記号を種として関連候補が出る。

行単位の不正は当該行を落として読み込みを続け、落とした行数を warning に含める（§14 と同じ）。

### 19.11 ライセンスと帰属

適用する規約は `docs/licensing-policy.md` の三層 attribution モデルである。§15 と同じく、本節はその 3
層を記号データに対して具体化する。

`symbol.tsv` の先頭コメント行に次を記す。

- 由来元（Mozc `symbol.tsv` と参照した revision）。
- ライセンス（BSD-3-Clause © Google）。
- ルート `THIRD_PARTY_LICENSES` への参照。
- porter のバージョン。

CLDR は使わないため、絵文字データのようなバージョン上限の記録（§7.3）は持たない。

ルート `THIRD_PARTY_LICENSES` の Mozc の節は、記号データと絵文字データで 1 つにまとめる。
SPDX `BSD-3-Clause`、原著作権表記、全文（第 3 条項を含む）、派生である旨を持ち、格納パスに `data/symbol.tsv` と
`data/emoji.tsv` を並べる。

chain 表（`core/src/SymbolChainTable.cpp`）は帰属の対象にならない。
族の構成を原典のカテゴリ列や行順から導かず、Unicode の括弧の定義と `docs/bracket-pairing-spec.md` §4.1
の対応表から自前に書くためである（§19.4）。
この線を越えて原典から族を導く場合は、ソースファイルにもヘッダを付け、本節へ追記する。

原典のファイルをそのまま同梱しない（§15.4 と同じ）。

### 19.12 テスト観点

M62-C の受け入れ条件（`plans/windows-port-roadmap.md` M62-C）に対応する検証は次で行う。

| 対象 | 検証内容 | 層 |
|---|---|---|
| かな読み引き（§19.3） | 完全一致だけが当たること。前方一致で当たらないこと。32 文字超で引かないこと。上限 4 件。`rank` 降順とコードポイント昇順の順序 | core |
| chain の展開（§19.4） | `「` を種として `『【〔（` が定義順で出ること。追加した候補に種が含まれず、種そのものは元の位置に残ること。種が複数あるとき最上位の 1 件だけが展開されること。族をまたがないこと | core |
| chain と読み引きの合成（§19.4、§19.5） | `かぎかっこ` の候補列に読み引きの結果が出て、その族が chain で広がること。既存候補と重複する族の要素が落ちること | core / tsf-tip |
| 件数上限の適用順（§19.5） | 記号と絵文字の両方が有効なとき、切り詰めが末尾の追加より前に行われること。超過分が絵文字側から落ちること。両方の ON / OFF で変換候補の件数が変わらないこと | host |
| 注釈（§19.6） | 読み引き候補が `name_ja` を、chain 候補が表の和名を持つこと。確定文字列に注釈が入らないこと | core / tsf-tip |
| 学習の除外（§19.7） | 記号候補の確定で学習ストアが変わらないこと。`shown` に `source == "symbol"` が載らないこと | tsf-tip / learning |
| 設定の伝播（§19.8） | `symbolRewriter` が settings.json から Host の runtime settings、Handshake 応答、TIP の保持値まで届き、chain の展開が実際に有効になること | settings / host / ipc / tsf-tip |
| M61 との境界（§19.9） | 候補窓からの `「」` 確定でペアリングが発火しないこと。chain 表の括弧対の綴りが `docs/bracket-pairing-spec.md` §4.1 の対応表と一致すること | tsf-tip / core |
| 既定 OFF（§19.10） | `symbolRewriter == false` で候補、確定、学習が不変であること | tsf-tip / host |
| フォールバック（§19.10） | ファイル不在で他の候補が壊れないこと。データが無くても chain が働くこと。不正行が落ちて読み込みが続くこと。warning が 1 回であること | host |

再ポートの検証には原典の全量を使わず、テストに必要な行だけを含む固定サブセットをリポジトリへ置く（§16 と同じ）。
