## 1. 目的と範囲

AZIK とかな入力の利用者が、打ち方を変えずにこの IME を使えるようにする。

範囲に含めるもの:

- AZIK（§3）。
- かな入力の JIS 配列（§4）。
- カスタムローマ字表で、英字の大文字と小文字を区別すること（`docs/legacy-parity-spec.md` §5.1）。

範囲に含めないもの:

- US 配列のかな入力（legacy の「かな入力（US）」）。Windows の日本語 101 配列での配置を確かめてから別の
  マイルストーンで扱う。
- legacy の表エディタ、プリセット、表の書き出し。
- ローマ字入力とかな入力をキーで切り替えること（Alt+カタカナひらがな。`docs/tsf-deep-integration-spec.md` §3.1）。
  切り替えは設定 `inputStyle` で行う。
- カタカナ入力モード。

## 2. 設定 `inputStyle`

| 値 | 入力方式 | 区分 | 表 |
|---|---|---|---|
| `default` | ローマ字 | 内蔵ローマ字表 | `RomajiKanaConverter` の内蔵表（`docs/legacy-parity-spec.md` §5.4） |
| `azik` | AZIK | 表駆動 | 内蔵の AZIK 表（§3） |
| `kanaJis` | かな入力（JIS 配列） | かな | §4.2 の表 |
| `custom` | カスタム | 表駆動 | 利用者の TSV（`docs/legacy-parity-spec.md` §5） |

- 既定値は `default` とする。
- 値が無い、文字列でない、上の 4 値以外のときは `default` とする。TIP、Host の `SettingsStore`、設定アプリは
  同じ列挙で読む。
- `azik` と `kanaJis` を知らない古い版は、この値を `default` として読む。古い設定アプリは読み込み時に
  列挙外の値を取り除き、保存するとキーを書き戻さない。
- TIP は `settings.json` の変更を読み直して反映する。進行中の composition は、始めたときの入力方式のまま
  続ける（`docs/legacy-parity-spec.md` §5.3 のカスタム表の差し替えと同じ）。
- 設定アプリは入力ペインの「入力方式」の節に置く。項目名は「ローマ字・かな入力」、選択肢は「ローマ字（標準）」
  「AZIK」「かな入力（JIS 配列）」「カスタム」とする。`customRomajiTablePath` は `custom` のときだけ有効にし、
  それ以外では無効にする（`docs/settings-app-spec.md` §3.2 の条件つきの項目の規約）。

## 3. AZIK

### 3.1 表の出典と取り込みの条件

- 表の出典は AzooKeyKanaKanjiConverter の
  `Sources/KanaKanjiConverterModule/InputManagement/InputTables/defaultAzik.swift` とする。版は
  `bbef9d2d99a2e9e69ac3f7e2e07b08474de59a81`（`legacy/Core/Package.swift` が固定する revision）で、
  規則は 569 件である。ライセンスは MIT（Copyright (c) 2023 Miwa / Ensan）。上流は、この表をどの資料から
  起こしたかを記していない（上流 #227）。
- AZIK の方式は木村清氏の考案である。原典「AZIK総合解説書」の参照先は、Internet Archive の版
  （`https://web.archive.org/web/20201101065109/http://hp.vector.co.jp/authors/VA002116/azik/azikinfo.htm`）とする。
  原典に明示のライセンスや利用条件は無い。実装について「多くの方々がAZIKの実装プログラムやデータを公開」
  「以下の説明はこういったAZIKの亜種や応用を制限するものではありません」と書かれている。
- 実装は、上の版の表を core の内蔵表へ写す。写すときは `THIRD_PARTY_LICENSES` に、上流の MIT の表記と、
  AZIK の考案者を記す。上流の版を上げるときも、同じ条件で写し直す。
- legacy は、表を引く前に記号を全角へ写す（`-` は ー、`.` は 。、`[` は 「 など）。上流のキーのうち全角の文字は
  その結果なので、Windows 版の表では打鍵した ASCII に戻す。

| 上流のキー | Windows 版のキー | 出力 |
|---|---|---|
| `；` | `;` | っ |
| `：` | `:` | ー |
| `z。` | `z.` | … |
| `z、` | `z,` | ‥ |
| `zー` | `z-` | 〜 |
| `z「` | `z[` | 『 |
| `z」` | `z]` | 』 |

- 単独の `-` の規則（`-` → ー）を足す。上流の表に `-` の規則は無く、legacy では全角へ写した ー がそのまま読みに
  入る。表駆動の経路は `-` を表へ渡すので（`docs/legacy-parity-spec.md` §5.4）、規則が無いと読みに ASCII の `-` が残る。
  この規則で、`-` の打鍵の結果は legacy と同じになる。`z-` は前方一致で先に当たるので 〜 のままである。

上流の規則は、キーが 1〜3 文字、出力が 3 文字以下で、`docs/legacy-parity-spec.md` §5.1 のカスタム表の上限に収まる。
写した表の規則は、上流の 569 件に、`-` と §3.2 の `ji` を足した 571 件になる。

### 3.2 Windows 版の差

- `ji` → じ を足す。上流の表には無い（上流 #360）。`ji` はほかのキーの前方一致にならないので、ほかの打鍵列の
  読みは変わらない。
- 全角のセミコロンとコロンを、読みに入れる手段は無い。`;` は っ、`:` は ー になる（上流 #361。legacy と同じ。
  `:` の例外は §3.3 の絵文字検索だけ）。
- AZIK の表に `n` だけの規則は無い。確定するときに残った `n` は英字のままになる（legacy と同じ）。ん は `nn` か
  `q` で打つ。

### 3.3 打鍵の処理

- AZIK は表駆動の入力方式（§5）として、カスタム表と同じ経路で変換する。`RomajiKanaConverter::Feed` が
  内蔵表に対して行う特例（子音の重ね打ちの促音、`n` の後の子音の ん、`nn` の後の母音の持ち越し、`n'` の区切り）は
  通さない。AZIK では `kk` が きん、`nt` が にち、`nz` が なん で、これらの特例と衝突するためである。
- AZIK の表に大文字の規則は無いので、Shift 付きの英字も小文字の規則で引く（`docs/legacy-parity-spec.md` §5.1）。
- 記号キーは、表が続けられる文字なら表へ渡す（`docs/tsf-deep-integration-spec.md` §3.5 の処理順 3）。
  `;` と `:` は単独の規則があるので表へ渡り、`.` `,` `[` `]` は `z` の後だけ表へ渡る。表が続けられない記号は
  §3.5 の表で全角にする（`.` は 。）。`-` は記号の表を通らずに表へ渡るので（`docs/legacy-parity-spec.md` §5.4）、
  §3.1 の規則で ー、`z` の後は 〜 になる。
- カッコ補完（`docs/bracket-pairing-spec.md`）が有効なアプリでは、`[` と `]` は §3.5 の処理順 2 のカッコ補完が
  先に受け取る。そのため `z[` `z]` は 『 』 にならない（カスタム表と同じ）。
- composition が空のときの `:` は、絵文字検索（`docs/candidate-rewriter-spec.md` §11）が有効なら、AZIK の ー より先に
  絵文字検索に入る（§3.5 の処理順 1）。
- 表は配列が生んだ文字で引く。US 配列では、`:` は Shift+`;` で打つ。
- 一括変換の蓄積中は、raw 入力を AZIK の表で読みにする（`docs/romaji-batch-conversion-spec.md` §4.1 のカスタム表と同じ）。

## 4. かな入力（JIS 配列）

### 4.1 キーの引き方

- かなは、キーの物理位置（スキャンコード）と Shift の有無で引く。配列ドライバの生む文字や VK では引かない。
  かなの刻印は物理位置に付くので、日本語 106/109 配列のドライバを 101 配列に設定した機械でも同じかなになる。
  配列が生む文字では、ろキーと ¥ キーが同じ `\` を生み、区別できない。
- スキャンコードは、キーメッセージの `lParam` のビット 16〜23 から取る。拡張フラグ（ビット 24）が立つキーは
  表を引かない（テンキーの `/` は `/` キーと同じスキャンコードを持つ）。
- テンキーの VK（`VK_NUMPAD0`〜`VK_NUMPAD9`、`VK_ADD`、`VK_SUBTRACT`、`VK_MULTIPLY`、`VK_DECIMAL`、`VK_DIVIDE`）は、
  スキャンコードより先に VK で見分け、表を引かない。
- キーメッセージのスキャンコードが 0 のとき（VK だけを送る注入など）は、現在の配列で VK をスキャンコードへ写す
  （`MapVirtualKeyEx`。`docs/tsf-deep-integration-spec.md` §3.5 の ¥ キーの判定と同じ）。
- Shift は左右を区別しない。CapsLock の状態は見ない。Ctrl、Alt、Win が押されているキーは表を引かず、
  ローマ字入力と同じに扱う。
- 表は core の純関数が持つ。入力はスキャンコード、拡張フラグ、Shift の有無で、出力はかなか「表に無い」である。
  表に無いキーは、ローマ字入力と同じに扱う。
- TIP は、表のキーを `docs/tsf-deep-integration-spec.md` §3.5 の処理順（絵文字検索の入口、カッコ補完、カスタム表、
  `n` の後のアポストロフィ）と記号の全角化の表より先に、本書の表で引く。配列が生む文字（Shift+8 の `(` など）では、
  これらの処理に入らない。
- 表のキーのうち、`docs/legacy-parity-spec.md` §1.5.3 の第 1 層が `Input` を返すもの（英字・記号のキー、
  Shift 付きの数字キー、読みがあるときの数字キー、候補窓の表示中の `0`）は、第 2 層で文字を解決するときに表のかなを
  載せる。第 1 層が Idle で素通しを返す数字キーは、TIP が写像より前に取り込んで composition を始める（§4.4。
  `numberRewriter` が Idle の数字を取り込む前処理と同じ位置）。
- 表の一次情報は JIS X 6002 のかな配列とする。上流の `defaultKanaJIS.swift`（§3.1 と同じ版）は照合に使う。
  上流は配列が生む文字で引くため、ろキーの単打が ー になる（上流は `＼` の規則に、配列の設定に依存するという注記を
  付けている）。本書の表は、スキャンコードでろキーと ¥ キーを分ける。

### 4.3 濁点・半濁点の合成

- ゛ のキーは、カーソルの直前の読みの 1 文字が次のどれかなら、その文字を濁音に置き換える。
  う→ゔ、か行→が行、さ行→ざ行、た行→だ行（ち→ぢ、つ→づ を含む）、は行→ば行。
- ゜ のキーは、カーソルの直前の読みの 1 文字が は行 なら、その文字を半濁音に置き換える。
- 合成できないとき（読みが空、直前が合成の対象でない、直前がすでに濁音か半濁音）は、単独の ゛（U+309B）か
  ゜（U+309C）を読みに足す。読みが空なら、その 1 文字で composition を始める。
- 合成した文字は 1 文字として扱う。Backspace は合成した文字を 1 回で消す。
- 合成するのは読みの中の文字だけで、確定した文字列には及ばない。

### 4.4 入力状態ごとの扱い

- 読みが無いとき（Idle）: 表のキーは composition を始める。数字キーの段（`0x02`〜`0x0B`）も同じで、
  ローマ字入力で Idle の数字をアプリへ渡す規則（`docs/legacy-parity-spec.md` §1.5.3）は当てない（§4.1 の前処理）。
  テンキーはローマ字入力と同じに扱う。
- 読み入力中とライブ変換の表示中: かなを読みに足す。未確定のローマ字は持たない。
- 候補窓の表示中: Shift なしの `1`〜`9` のキー（`0x02`〜`0x0A`）は候補番号のまま（`docs/legacy-parity-spec.md`
  §1.4）。そのほかの表のキーは、ほかの文字入力と同じく選択中の候補を確定し、そのかなで次の composition を始める。
- Space の応答を待つ間: ほかの文字入力と同じく保留し、窓が開いた後に再生する（`docs/legacy-parity-spec.md` §1.2）。
- 英数モードと IME Off: 表を引かない。キーはローマ字入力と同じくアプリへ渡る。
- 表が生む 、 と 。 は、`docs/tsf-deep-integration-spec.md` §3.5 の明示句読点と同じに扱う。読みが無いときの
  半角の候補と、`punctuationConversion`（同 §3.5.1）も同じである。
- カッコ補完（`docs/bracket-pairing-spec.md`）は、表が生む 「 と 」 にだけ働き、ローマ字入力で `[` `]` から
  取り込んだ 「 」 と同じに扱う。配列が生む文字ではカッコを判定しない（§4.1）。Shift 付きの数字キー（`(` `)` `"` `'`
  を生む配列のキー）は ゅ ょ ふ ゃ になり、Shift なしの `0x1B`（゜）と `0x2B`（む）もカッコ補完の対象にしない。

## 5. 表駆動の入力方式（AZIK とカスタム）

AZIK とカスタムは、表のキーの並びをかなへ変える同じ経路で変換する。これを表駆動の入力方式と呼ぶ。
内蔵ローマ字表と違い、Host は表を持たず、生ローマ字から読みを作り直せない。

他の spec で「カスタムローマ字表（`inputStyle=custom`）」を条件とする規則は、AZIK にも同じく当てる。

| 規則 | 正典 |
|---|---|
| `RomajiKanaConverter::Feed` の特例を通らない | `docs/legacy-parity-spec.md` §5.4 |
| `alt_readings`（`nn` の後の母音の曖昧さ）を送らない | `docs/legacy-parity-spec.md` §5.4 |
| 表が続けられる記号を表へ渡す（処理順 3）。`n'` の区切りに使わない | `docs/tsf-deep-integration-spec.md` §3.5 |
| F9・F10 は、生ローマ字ではなくかなから作り直したヘボン式で綴る（一括変換の蓄積中は raw 入力） | `docs/tsf-deep-integration-spec.md` §3.6 |
| `raw_keys` を送らない | `docs/typo-correction-learning-spec.md` §12.13 |
| M63 は働かない | `docs/mixed-english-auto-conversion-spec.md` §5 |
| 一括変換は表の出力を表示と変換の読みに使い、蓄積中は始めたときの表を保つ | `docs/romaji-batch-conversion-spec.md` §4.1 |
| 英単語候補（M60）は、TIP が自分の表で生ローマ字を読みと照合し、一致するときだけ送る。一括変換では 1 文節の要求に限る | `docs/inline-english-candidate-spec.md` §4.1・§4.1.1 |

AZIK とカスタムの違いは次のとおり。

- AZIK の表は内蔵で、読み込みに失敗しない。カスタムは TSV が無い、読めない、有効な規則が 0 件のとき内蔵
  ローマ字表を使う（`docs/legacy-parity-spec.md` §5.4）。
- ファイルの監視とホットリロード（同 §5.3）はカスタムだけにある。
- AZIK の表は小文字の規則だけを持つので、英字の大文字と小文字の区別（同 §5.1）は AZIK の結果を変えない。

## 6. かな入力での他の機能

かな入力では、生ローマ字も打鍵した ASCII も無い。ローマ字を素材にする機能は次のとおり扱う。

| 機能 | かな入力での扱い |
|---|---|
| 一括変換（M58。M58-C の AI 整文を含む） | 働かない。`batchRomajiConversion` が true でも通常の入力にする |
| 英単語候補（M60）と日英混在の自動変換（M63） | 生ローマ字を送らない |
| `raw_keys`（M35・M55） | 送らない。TIP が送るのはローマ字入力の打鍵だけである（`docs/typo-correction-learning-spec.md` §12.13）。読みに対する補正は変えない |
| `alt_readings` | 送らない |
| F9・F10 | かなから作り直したヘボン式で綴る（カスタム表と同じ。`docs/tsf-deep-integration-spec.md` §3.6） |
| 絵文字検索の `:` の入口（`docs/candidate-rewriter-spec.md` §11） | 使わない。`:` のキーは け を生む |
| Unicode 入力（Ctrl+Shift+U、`docs/legacy-parity-spec.md` §6） | 16 進の数字は配列が生む文字で受け、かなに写さない |
| 英字の入力 | 打てない。英字は英数モードか IME Off で打つ。Shift 付きの英字のキーもかなを生む |
| 数字の入力 | 主キーの数字の段はかなを生むので、数字はテンキーで打つ。読みが無いときのテンキーの数字は、ローマ字入力と同じく `numberRewriter` が ON のときだけ composition を始める |
| 計算の動的候補（M62-E、`docs/candidate-rewriter-spec.md` §20.6） | 出ない。計算には読みの末尾の `＝` が要るが、かな入力では `=` のキーが ほ を生み、テンキーにも `=` は無い。規則は変えない |

ライブ変換、予測、学習、セーフ入力は、読みを素材にするので変えない。

## 7. legacy との差

- AZIK: `ji` を足した（§3.2）。表を引く前に記号を全角へ写さず、ASCII のキーで表を引く。全角のキーを ASCII へ
  戻して写し、`-` の規則を足したので（§3.1）、`ji` のほかの打鍵の結果は legacy と同じになる。カッコ補完が有効な
  アプリの `z[` `z]` は 『 』 にならない（§3.3）。
- かな入力: legacy は配列が生む文字で引くので、ろキーの単打が ー になる。Windows 版はスキャンコードで引き、
  ろキーは ろ になる（§4.1）。
- かな入力: legacy は濁点・半濁点を表の規則（`か＠` → が など）で合成する。Windows 版はカーソルの直前の 1 文字と
  合成する（§4.3）。結果は同じである。
- US 配列のかな入力は Windows 版に無い（§1）。

## 8. テスト計画

| 層 | 確かめること |
|---|---|
| core | AZIK の表が上流の 569 件に `-` と `ji` を足した 571 件で、全角のキーが §3.1 の表のとおりに写る。表駆動の経路で `kk` → きん、`nt` → にち、`nn` → ん、`-` → ー、`z-` → 〜 になり、`Feed` の特例を通らない。確定時に残る `n` は英字のまま |
| core | かなの表の全キーについて、Shift の有無ごとの出力が §4.2 と一致し、表に無いキーと拡張フラグの立つキーで「表に無い」を返す。§4.3 の合成（か＋゛ → が、う＋゛ → ゔ、は＋゜ → ぱ、あ＋゛ → あ゛、読みが空の ゛、が＋゛ → が゛） |
| core | カスタム表の大文字の規則が Shift 付きの打鍵だけに当たり、大文字の規則が無いときは小文字の規則に落ちる。表に当たらない英字と一括変換の扱い（`docs/legacy-parity-spec.md` §5.1） |
| TIP | `inputStyle` の `azik`・`kanaJis`・列挙外の値の読み込み。進行中の composition が始めたときの方式を保つ |
| TIP | かな入力で、スキャンコードが 0 のキーを VK から写し、テンキーの VK は表を引かない。ろキーと ¥ キーを分ける。Idle の数字キーで composition が始まり、候補窓の表示中の `1`〜`9` が候補番号になる。英数モードでアプリへ渡る |
| TIP | かな入力の 、。 が明示句読点として働き、「 」 だけでカッコ補完が働く（Shift+8・Shift+9 では働かない）。F9・F10 がヘボン式になり、Ctrl+Shift+U の 16 進がかなに写らない |
| TIP | AZIK とかな入力で `raw_keys` と `alt_readings` を送らず、かな入力で生ローマ字を送らない。かな入力で一括変換と `:` の入口が働かない。AZIK の `;` `:` が §3.3 の処理順で表へ渡り、F9・F10 がヘボン式になる |
| settings | schema の列挙、`SettingsStore` の読み込み、設定アプリの選択肢と、`customRomajiTablePath` が `custom` のときだけ有効になること |
